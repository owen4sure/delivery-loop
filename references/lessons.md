# 事故與規則

這些規則來自一個系統導入專案中實際出過的問題或使用者的明確要求（已去除公司與個人資訊），適用於任何用 AI agent 做的網站、網頁、系統專案；標「預防」的是還沒發生、但後果嚴重而先定下的規則。規則看起來太嚴、或不知道該怎麼套用時，看當初發生了什麼事。

編號同時用在 [evals/scenarios.md](../evals/scenarios.md)。

## L1 一個測試被擋，整個專案停擺
**發生**：瀏覽器測試被平台限制擋下，agent 回報「等待中」，其他能做的修正也全部停了。
**規則**：阻礙只擋依賴它的工作單。停之前跑 `--stop`，有其他可做的工作單就繼續。

## L2 被拒絕後換方式重試
**發生**：某個操作被平台拒絕，agent 改用另一個工具、另一個 agent 身分再試一次。
**規則**：平台或使用者拒絕的動作，不換工具、不換身分、不換說法繞過。記成 X 阻礙，回報使用者。

## L3 工作佇列空了，就說「在等外部」
**發生**：派工佇列沒有工作，agent 宣稱只剩外部依賴；其實有一整個需求還沒拆成工作。
**規則**：沒有工作單不等於做完。里程碑沒有工作單、或需求沒有對應的工作單時，先拆解。

## L4 同一個失敗一直重跑
**發生**：共用快取讓「資料保存比對」出現差異，agent 一直重跑，想等到剛好沒差異的那一次。
**規則**：沒有新資訊不重跑。先找出是誰在寫入，區分正常的 session／快取活動和真正的資料變更。

## L5 已回答的問題又被問一次
**發生**：使用者已確認的工時和假日規則，在新的進度紀錄裡被漏掉，agent 又問了一次。
**規則**：已確認的決定寫在 GOAL.md「已確認的決定」。問之前先查，不要因為最新的紀錄沒寫就重問。

## L6 一題一題彈出問題
**發生**：使用者要求把待答問題集中，agent 還是一題一題跳出來詢問。
**規則**：問題寫進 QUESTIONS.md，在交接點一次給。只有安全問題或必要動作不能等時，才立即提出。

## L7 監督者和主線都在派工
**發生**：監督 session 和主線各自派工作給同一個工作線，造成重工和衝突。
**規則**：只有整合者派工。監督者只驗收與回報。

## L8 build 成功被當成驗收
**發生**：「build 通過、HTTP 200、測試全數通過」被回報成「功能完成」，但這些都沒有證明畫面上實際能操作。
**規則**：證據等級。驗收標準寫 ui，就要有 ui 等級以上的 PASS 證據。

## L9 新 session 被當成多一個瀏覽器
**發生**：為了並行測試開了新 session，以為它有自己的瀏覽器和資料庫；其實它沒有可用的瀏覽器，測試從未執行，卻被算成「進行中」。
**規則**：開之前先確認新 session 實際有哪些工具。記錄實際上是誰操作、誰測試。

## L10 沒有截止日，工作無限擴張
**發生**：目標寫成「全部頁面完全客製、零原生殘留」，agent 連續跑了兩週，說不出什麼時候會完成。
**規則**：GOAL.md 必須有截止日與里程碑。到期就交出現況報告。回報時用剩餘的工作單張數來估時間。

## L11 舊的停止指令被擴大
**發生**：使用者說「停止這一輪壓力測試」，之後 agent 把它當成「所有測試都停」。
**規則**：只停使用者指定的範圍。之後無關的工作，要先核對原句才能套用。

## L12 不知道的金額填成 0（預防）
**風險**：匯入舊資料時，如果把缺少的餘額填成 0，報表看起來平衡，其實是錯的，而且很難事後發現。
**規則**：不知道就保持空白，並開一個 Q。不要猜，也不要填 0。

## L13 主機吃緊，想停掉別的服務
**發生**：測試主機記憶體不足，agent 提議停掉同一台主機上其他專案的服務。
**規則**：資源不足要附上證據回報。不能自己停掉不屬於這個專案的服務、新增服務或放寬檢查；需要這樣做，就開一個問使用者的 Q，附建議做法和「請回覆」。

## L14 公開說明寫滿歷史漏洞
**使用者要求**：公開更新聚焦在成果與驗證，不列歷史漏洞故事；內部的失敗與根因紀錄要完整保留。
**規則**：對外寫成果、驗證和目前限制；失敗和根因留在內部紀錄。不刪紀錄，也不改寫歷史。

## L15 作者自己驗收自己
**發生**：作者用管理員帳號自己測試、自己宣布通過，掩蓋了一般角色的權限錯誤；改用只有該角色權限的帳號測試才發現。
**規則**：done 需要非作者的 reviewer。risk 是 data 或 access 時不能豁免。

## L16 流程文件比產品還多
**發生**：35 小時內產生約 2,000 個流程檔（其中 762 個 JSON、229 個審查檔，共 11MB）。每個小單元都要凍結、寫 SHA 收據、再做獨立審查，但真正的畫面驗收一直寫著「尚未驗收」。
**規則**：證據就是原始產物（截圖、測試輸出）。審查份量跟風險成正比；版本對應只在發布時做一次。

## L17 一張工作拆成很多輪派工
**發生**：主線在 35 小時內呼叫了約 580 次派工、傳訊、等待；worker 每做完一個小步驟就「已停止」，等主線再派下一步。
**規則**：一張工作單＝一次派工。同領域下一張準備好了就直接接著做。

## L18 同一個 thread 跑了兩週
**發生**：主 thread 從開工一路跑到交付前，紀錄檔超過 1GB，平均 context 約 26 萬 token，35 小時內被壓縮 19 次。每次呼叫都要重讀巨大的 context，又慢又貴，壓縮後還會遺忘決定。
**規則**：狀態放在檔案裡。context 超過約 150k 或里程碑結束，就寫回檔案、開新 session。

## L19 監督喚醒每次重貼長規則
**發生**：監督 session 每次喚醒都附上 1,800 字以上（最後長到 8KB）的規則，35 小時內喚醒 70 次，大多只回「狀態沒變」，卻用掉約 1.4 億 input token。
**規則**：喚醒提示一句話，只跑檢查程式看摘要；規則放在 skill 和 GOAL.md。

## L20 自己訂的規則被當成外部阻礙
**發生**：使用者說過「資料庫千萬不能出問題」，agent 解讀成連本機測試都不能寫入，把「沒有安全的寫入環境」記成外部阻礙。結果所有要存檔的流程都標成卡住，只驗到打開視窗再按取消。使用者授權從備份複製一個測試站後，約 35 分鐘就驗完五個存檔流程。
**規則**：保護資料靠備份和測試副本，不是靠不驗。規則或授權範圍擋住驗收，就寫成問使用者的 Q，附建議做法和「請回覆」。

## L21 授權不夠走到驗收，做到一半才停
**發生**：使用者授權開測試站，但同一段寫了「不新增服務」。資料面驗完後，agent 才發現用瀏覽器看新版畫面需要另開一個網頁程序，於是記成外部阻礙並停下。
**規則**：收到授權後，先把走到驗收等級的整條路看一遍（資料、程式版本、瀏覽入口、帳號、寄信），不夠的一次問完再動手。

## L22 停下來了，使用者卻看不懂要做什麼
**發生**：回報寫著「X1／X2 僅對新站解除」「候選版測試站尚無合法瀏覽入口」，接著只說恢復條件在待答清單。使用者看不懂卡在哪，也不知道自己回一句授權就能繼續。
**規則**：回報寫給不寫程式的人看。等使用者時，最後一行給照抄就能回的句子。

## L23 主要流程卡住，就去做周邊小事
**發生**：存檔流程卡住後，agent 陸續新增「鍵盤 Tab 能不能繞一圈」「打開預覽再按取消」這類工作單。完成的 9 張裡，沒有一張驗到真的存檔。
**規則**：新工作單要指出來自哪條需求或哪個實際缺陷。主要流程卡住時，先把卡點變成問使用者的 Q。

## L24 交接後舊 thread 還在接指令，監督掛在大 thread 上
**發生**：主線交接給新 session 後，使用者把新指令貼到舊 thread，舊 thread 照做，新 session 只能停下來等它交接；監督排程也一直掛在 context 很大的舊 thread 上，每次喚醒都要重讀整個 context。
**規則**：GOAL.md 標頭寫 integrator；舊 thread 收到指令就指向新 session。監督喚醒放在新開的小 thread。

## L25 要問同事的事，使用者從來不知道
**發生**：agent 把要問兩位同事的事寫在一個很深的輸出檔，回報只說「待答兩項」。使用者以為都問完了，直到快上線才發現從來沒人去問。
**規則**：問題文件是給人看的，每題有背景和建議答案；要轉問的附可以直接轉傳的訊息。每次有新題目，都在對話裡說「新增幾題、要轉問誰」。

## L26 一直說沒問題，其實方向有缺口
**發生**：使用者多次問「還有沒有問題」，agent 都說沒有。後來逐項檢查，才找到沒整理給使用者的待問事項，以及把安全規則解讀過頭而卡住的地方。
**規則**：開工訪談，中途接手也要做方向檢查。用一頁「我理解你要的」讓使用者確認，不能只回答「沒問題」。

## L27 測試留下的東西越堆越多，沒人敢刪
**發生**：本機累積了十幾個測試站、約 45GB 的 Git 暫存檔和重複副本。使用者怕刪錯影響專案，一直不敢動，空間只能一直買。
**規則**：建立的東西當下記進 CREATED.md；用完照嚴格標準清理，先隔離再刪除；不是自己建的，證明不了就問使用者。

## L28 驗收者看的是作者給的證據
**使用者要求**：防止作者寫錯或造假證據。審查者如果只讀作者的交接和截圖，作者錯了一樣會通過。
**規則**：盲測驗收：全新的 session，只給驗收標準和測試環境，自己操作一遍、自己留證據（by=驗收者）。ui 以上的證據必須是截圖、錄影或瀏覽器紀錄，文字報告不算。

## L29 為了不停下來，一個 agent 卡住就全部等
**使用者要求**：大型專案要像公司一樣運作：需要審核或等答案的部分先放著，其他不受影響的工作繼續並行，不要因為一個小問題整個停下來。
**規則**：卡住的只停那一張；執行者把問題交回整合者、換下一張；有互不影響的工作就並行，數量看電腦資源和額度。
