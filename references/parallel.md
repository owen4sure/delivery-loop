# 並行、派工、盲測與交接

像公司一樣分工：有互不影響的工作單、資源不衝突、電腦資源和額度夠，就並行。整合者像專案經理，主要時間花在派工、整合和處理問題，不是自己一張一張做。

## 選哪一種

| 情況 | 做法 |
|---|---|
| 小改動、沒有能獨立拆出去的部分 | 自己做，不開 subagent |
| 一張工作單、交出一個結果（實作、測試、分析） | 短期 subagent |
| 驗收動到錢、資料、權限的工作單，或里程碑整合驗收 | 盲測 subagent 或新 session（見下方） |
| 已有閒置的執行者，有相關脈絡和資源 | 重用它，先看它最後的交接；context 超過約 150k 的不重用，改開新的 |
| 一個領域要跨好幾個里程碑、需要長期脈絡或獨立環境 | 長期工作線 session（使用者授權且平台支援時） |
| 會寫到同一個資料庫、快取、build 或別人的路徑 | 排隊，由現有 owner 依序做；多開 branch 解決不了資源衝突 |
| 執行者卡在一個問題 | 問題交回整合者寫進 QUESTIONS.md，執行者換下一張，不在原地等 |
| 沒有具體可做的工作單，或沒有額度 | 不開，等真正的前置事件 |

不要為了繞過 subagent 數量限制、平台拒絕或額度而另開 session。

## 開幾個

- 檢查程式列出的「這一波可以並行」就是一批可以同時開工的工作單：彼此資源不衝突，高風險的排前面。「要排隊」的等前面的做完再開。

- 看電腦記憶體和額度決定，預設上限 4 個。記憶體吃緊（例如虛擬記憶體快滿、電腦變慢）或額度快用完，就減少。
- 協調訊息比實作還多時，代表拆得太細，減少並行、加大每張工作單。
- 要算所有工作線和它們的 subagent，不是每個 session 各有一份額度。

## 開之前確認

1. 要交出去的工作單編號，以及並行為什麼能縮短時間。
2. 現有執行者清單，以及為什麼不能重用。
3. 新 session 真的有工作單需要的工具，例如瀏覽器、資料庫連線、編譯器。新 session 不會自動多出瀏覽器、資料庫或額度；worktree 只隔離原始碼。
4. 使用者對開 session、傳訊息的授權。安裝這個 skill 不等於授權。

缺工具就把那張工作單維持 ready 或寫成問題，不要假裝已經開始。要記清楚實際是誰操作、誰測試、誰驗收。

## 派工內容

```text
工作單：T05（連結到工作單檔）
基準版本：<commit>
工作目錄：你自己的 git worktree（例如 ../worktrees/T05）；開工前先跑一次相關測試，記下原本就失敗的項目
先讀：.done-done/LEARNINGS.md
你擁有：路徑／站台／快取命名空間／port
不能碰：共用資料庫寫入、build、部署、其他人的路徑
已確定的決定：（從 GOAL.md 摘要，不要附帳密或整份業務資料）
要先讀的 skill：（例如 UI 測試）
驗收：工作單上的驗收標準，證據格式照工作單範本，ui 以上要截圖或錄影
卡住時：把問題寫在交接紀錄並回報整合者，換下一張，不要停下來等
上限：最多 N 次嘗試；兩種修法都失敗就回報
交接：寫在工作單的「交接紀錄」，10 行內講完；長的輸出存成檔案附路徑。學到下次用得到的事，記一條到 LEARNINGS.md。做完一張就接下一張
```

## 盲測驗收的派工內容

```text
要驗：T05 的驗收標準（只貼驗收標準本身）
環境：測試站網址、測試帳號、怎麼登入
要做：自己操作每一條驗收標準，留截圖或錄影
不能：看作者的交接、截圖、程式修改內容或之前的對話；不能修改程式
回報：每條 PASS／FAIL，證據行加 by=你的名字；不通過就寫你看到的實際狀況
```

驗收者用的是全新的 session 或 subagent，不繼承前面的對話。它看到的狀況和作者說的不一樣時，以它看到的為準，退回作者處理。

## 交接內容

每次交接寫在工作單的「交接紀錄」：

- 基準版本和結果版本、改了哪些路徑、在哪個環境
- 每條驗收標準的結果：PASS／FAIL／PARTIAL／SKIP，附證據
- 受保護狀態有沒有差異
- 還沒做的、發現屬於別人的問題（附證據，不要自己動手修別人的範圍）
- 建立了哪些東西（同步寫進 CREATED.md）、釋放了哪些資源

整合者收到交接後：看實際證據檔 → 核對狀態後才釋放 lease → 照「獨立驗收」決定要不要盲測 → risk 是 data／access 的再做程式碼審查 → 把 worktree 的改動整合一次 → 更新工作單和 LOG.md。訊息說「做完了」不算數，證據才算。

## 程式碼審查的派工內容

```text
要審：T05 的程式碼改動（附 diff 或 commit 範圍）
重點：權限能不能被繞過、資料與金額算得對不對、輸入有沒有檢查、會不會刪到或改到不該動的資料
不用管：命名、排版這類風格問題
回報：問題依嚴重程度列出（嚴重的會擋住完成），附檔案與行號；沒問題就寫「沒有發現問題」，並在工作單標頭填 code_reviewer
```

## 長期工作線

只有在某個領域要跨多個里程碑、而且凡事經過整合者已經變成真正的瓶頸時才開。開之前，在 GOAL.md 或 LOG.md 寫下章程：

- 上層整合者、實際的 session 編號、負責的工作單或里程碑，以及第一張要做的工作單
- 擁有的路徑、環境、受保護資源
- 可以自己決定的事、能不能開 subagent、分到的額度（由誰調整）
- 保留給整合者的事：共用 runtime、build、schema、沒證明隔離的瀏覽器或資料庫操作
- 驗收方式、回報對象、交接位置、什麼時候算完成

工作線可以在自己範圍內選工作單、派 subagent、修完重測、接著做下一張，不必每步都問整合者。它不能拿走別人的路徑、改共用 runtime、擴大全域額度。跨領域問題附證據回報整合者。領域做完不代表整個專案做完；閒置的工作線不需要找事做。

## 轉移擁有權

1. 讓目前的執行者先做到一個交接點。
2. 核對 commit、未提交的修改、待驗收項目、執行中的程序與 lease。
3. 記下新 owner 和基準版本。
4. 舊 owner 和新 owner 不能同時做同一張工作單。轉移期間，新 owner 只能做唯讀檢查。

兩個 owner 修到同一個問題時：停止重複派工、保留未提交的修改、指定一個 owner，另一個在交接後當驗收者。

## 當機或脈絡遺失後

1. 先看 Git、執行中的程序、lease，再下任何指令。
2. 保留未提交的修改。只清除確定已被放棄的 lease；時間過期不代表寫入的程序已經停止。
3. 逾時代表結果未知，不代表失敗。先核對實際狀態，不要重送已經生效的操作。

## Codex 的工具

Codex 有 list_threads、read_thread、create_thread、send_message_to_thread、wait_threads 時，用這些工具，不要去改它內部的資料庫。

- 建立 session 是非同步的：記下回傳的實際編號，等它就緒後才算開始工作。
- 用指令開執行者時，`codex exec --worktree` 會在新的 git worktree 裡跑，適合並行。
- 重用 thread 前，要讀它的實際內容，不要只看標題。
- 換整合者時，把新 thread 的名稱與編號寫進 GOAL.md 標頭的 integrator，使用者才知道指示要傳給誰。
- 不要自己編 project、branch、環境或主機編號，也不要未經授權改模型設定。
