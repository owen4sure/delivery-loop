# 里程碑發布與部署

## 里程碑關卡

把里程碑標成 released 之前：

1. 這個里程碑的工作單全部 done 或 dropped。dropped 要有使用者同意；risk 是 data 或 access 的工作單不能悄悄放棄。
2. 凍結一個版本，讓原始碼、靜態資源、執行環境與安裝包都對應同一個版本。
3. 在這個版本上做「整合驗收」工作單：重跑受這次改動影響的驗收標準。沒受影響的舊證據可以沿用，但要寫明為什麼沒受影響。
4. 證據互相矛盾時（例如原始碼說有、畫面上沒有），先查清楚再驗收。
5. 安裝包要實際測過：入口能執行、依賴齊全。不能只確認清單檔存在。
6. 在 GOAL.md 標成 `[released rev=<版本> env=<local|staging|prod>]`，然後跑檢查。

範圍比較小的里程碑，可以排除無關的未完成工作，但要寫出影響分析，並由使用者接受。不能排除它交付範圍內已知的資料或權限問題。

## 三道關

| 關卡 | 代表 | 證據 |
|---|---|---|
| 本機可用 | 本機同一個版本，用真實角色帳號走完流程 | user 等級 |
| 可部署 | 安裝包加上部署步驟，在隔離環境實際演練過，包含還原 | 演練紀錄 |
| 正式站驗收 | 正式站已更新，並實際操作成功 | prod 等級 |

正式站沒有實際驗證，就只能說「可部署」，不能說「已上線」。

## 部署步驟

1. 事前檢查：目標主機可連線、空間、版本、正在跑的服務。
2. 更新前先做新的備份，並確認備份還原得回來。
3. 用有防護的方式套用：失敗時要停下來，不能半套。
4. 套用後檢查健康狀態，並實際操作關鍵流程。
5. 失敗時照事先寫好的回復步驟處理。

注意：資料庫 rollback 救不回 DDL（資料表結構變更）、檔案、佇列、已寄出的信或通知、外部系統的變更。每一種都要有各自的補救方式。除非整個部署入口真的支援從中斷處重來，否則不要寫「可以直接重試」。

## Git 與對外描述

- 本地細 commit，里程碑通過才 push。不 force push，也不改寫歷史來掩蓋問題。
- 對外（PR、公告）寫：現在能做什麼、驗證了什麼、目前的限制。不寫不必要的歷史漏洞故事。
- 對內（LOG.md、工作單）保留：失敗、根因、被否決的方案、沒驗到的範圍。
- 帳密、業務資料、私人證據不進 Git。

## 最終交付

交付報告包含：

- 可以使用的網址，以及要用什麼帳號登入
- 確切的版本與部署包位置
- 每個里程碑驗收到哪一道關，附證據
- 還沒解決的限制與待答問題（附上 QUESTIONS.md）
- 停用不再需要的定時監督，並照 [cleanup.md](cleanup.md) 清理測試站與暫存資料
- 之後的維護繼續用同一個 `.done-done/`：新狀況開新的工作單或里程碑
